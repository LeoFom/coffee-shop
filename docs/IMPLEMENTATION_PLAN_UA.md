## Архітектурні рішення

1. Залишити два репозиторії, Next BFF, Fastify, Prisma й окрему PostgreSQL Neon. Не витрачати перший етап на міграцію фреймворків чи monorepo.
2. API визначає ціни, права, доступність товарів, валюту й дозволені переходи замовлень. Redux не є джерелом істини про суму покупки.
3. Для мінімального запуску зберегти ADR-002: кошик і замовлення після входу. Додати повернення до товару/checkout після login. Гостьовий кошик і checkout — окреме наступне рішення, не випадкова зміна цього контракту.
4. Єдина валюта UAH. HTTP DTO й розрахунки — цілі копійки з суфіксом Minor; чинні DB Decimal зберігаються з точним перетворенням на межі. Історичні USD-замовлення, якщо з'явилися, не перейменовувати на UAH і не перераховувати заднім числом.
5. Стан замовлення, стан оплати й доставка — окремі поняття. COD-замовлення не стає Paid лише через створення або відправлення.
6. Для першого запуску ТТН можна створювати в кабінеті Нової пошти й заносити вручну в Coffeo. Автоматична купівля/створення накладної не є залежністю запуску.
7. Надсилання листа не повинне скасовувати вже записане замовлення. Для повторюваних повідомлень достатньо outbox у PostgreSQL і обмеженого dispatcher; Redis не потрібний. На Free не покладатися на незбережений background timer після HTTP-відповіді.
8. Схему змінювати новими міграціями на ізольованій тестовій БД. Не редагувати виконані міграції, не використовувати migrate reset у production і не змішувати БД Coffeo та Lead Finder.

Уточнення до першої редакції: Session.id уже існує; новий дубль ID не потрібний. Для COD запас зменшується при резервуванні в checkout, тому відправлення не списує його вдруге. Exactly-once доставка листа без підтримки провайдера не гарантується. Розділення HTTP 401/503, live delivery lookup і непрацюючий провайдер перевіряються окремо, а не за фактом наявності форми.

## Крок 3. Ціни, кошик та надійний checkout

Проблеми: A04–A06, A09–A10, A21.

## Крок 8. Приймання та запуск

Проблеми: A20, прогалини тестування всіх попередніх кроків.

- Автоматизувати негативні сценарії: чужі IDs, Customer→Admin API, недостатній stock, зміна ціни, дубль запиту, конкурентний checkout, 401/503, upstream timeout, прострочений reset, невдалий email, повтор status transition.

## Крок 9. Онлайн-оплата

Починати після стабільного COD-потоку й окремого вибору платіжного провайдера власником. Не припускати, що наявний enum PayPal означає готову PayPal-інтеграцію.

Додати PaymentAttempt/ProviderEvent, створення платіжної сесії із серверної суми UAH, перевірку підпису webhook, ідемпотентну обробку callback, звіряння суми/валюти/замовлення, retries і reconciliation. Browser return URL не є доказом оплати. Потрібні прострочення резерву й повернення stock при невдалій/простроченій оплаті, refund flow і журнал дій менеджера.

Готово, коли: sandbox успіх/відмова/повтор webhook/запізнілий callback/часткова відмова/повернення не дублюють оплату, замовлення чи залишки. Live credentials додаються тільки в серверні env; реальний платіж не проводиться без окремого доручення.

## Крок 10. Завершення додаткових модулів

Ці функції не повинні блокувати надійні продажі, але потрібні для реалізації всього початкового задуму UI:

- Лояльність: особиста MembershipPass, серверні правила eligibility, ledger нарахувань/списань/сторно, захист від повторного reward. Штамп нараховується за погодженою подією оплаченого/отриманого замовлення. QR генерується локально з непрозорим ідентифікатором; одного публічного UID недостатньо для списання. Для офлайн-кав'ярні потрібен окремий дозволений staff flow.
- Розсилки: endpoint підписки, double opt-in за погодженою політикою, версія згоди, відписка, suppression list і захист від спаму. Welcome coupon — тільки якщо реалізовано реальний перевірений механізм акції.
- Customers: admin-пошук клієнтів, їхні замовлення й службові нотатки з обмеженим доступом. Не відкривати всі персональні дані звичайному покупцю.
- Analytics: виручка за оплаченими продажами, скасування/повернення, залишки й топ товарів; за потреби — воронка без зайвого збору персональних даних.
- Activity: журнал адміністративних змін і важливих бізнес-подій із retention, а не необмежений запис кожної дії покупця.
- Settings: контрольовані налаштування магазину, контактів, доставки й програмних правил; API-ключі не віддаються UI.
- За потреби: гостьовий кошик/checkout з новим ADR, безпечне merge після входу, wishlist і варіанти пакування. Блог, вакансії та всі старі footer placeholders не є обов'язковими модулями магазину лише тому, що посилання були в шаблоні.

## Як виконувати й приймати кожен квиток

1. Прочитати відповідні розділи технічного документа й перевірити, чи залежності квитка вже реалізовані. Скласти короткий список файлів, API contract і даних, яких торкнеться зміна.
2. Додати змістовний regression/acceptance test для бізнес-інваріанта. Для row locks/unique/rollback використовувати PostgreSQL, не fake; для відображення/форм — браузер або вибірковий component test.
3. Реалізувати additive schema, domain service, serializer/API, BFF, UI саме в такому порядку, якщо квиток охоплює всі шари. Не залишати активну кнопку на неготовий endpoint.
4. Перевірити цільові тести, lint, typecheck, build; для DB change — validate, fresh migration та upgrade fixture. Після успішних перевірок не запускати без потреби ті самі jobs повторно.
5. У PR/звіті вказати кінцеву поведінку, API/web commit pair, migration, тести/run IDs, невиконані умови та rollback. Незапущений тест позначити незапущеним.
6. Власник приймає конкретний результат поточного етапу. Перехід до наступного кроку не є автоматичним наслідком завершення цього планування.

Квитки API й web можуть мати окремі PR, але release manifest узгоджує їхню контрактну версію. Важливі зміни не зливати в один великий PR усіх 11 кроків. Контент, ключі, ротація історичних секретів, merchant onboarding та платні рішення — окремі зовнішні залежності; їх не можна позначити завершеними комітом.
