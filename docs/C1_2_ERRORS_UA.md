# Coffeo C1.2 — відображення помилок і BFF

`nodejsFetchResult` повертає типізований `FetchResult<T>`: успішні дані або HTTP-статус, безпечний код помилки, request ID та `Retry-After`. Порожній масив товарів тепер означає успішну порожню видачу; 503 не перетворюється на `[]`. BFF перевіряє серверний `API_URL` і наявність внутрішнього ключа у production, обмежує вихідні заголовки й не друкує конфігурацію.

Проксі передає `Retry-After`, `x-request-id`, `Idempotency-Replayed` та **кожен** `Set-Cookie` окремо. Приватні відповіді мають `Cache-Control: no-store`. Каталог показує окремий стан недоступності з ручним повтором. Відсутній товар дає 404 через Next `notFound()`. Помилки читання профілю, замовлень або кошика не підміняються порожніми даними. Для помилки кореневого layout є `global-error`, для сторінок магазину — локальна error boundary.

Локальна перевірка із синтетичним API підтвердила: `/api/products` та `/api/v1/products` повертають HTTP 503 з `Retry-After: 5`, а браузер показує стан недоступності магазину. App Router віддає HTML сторінки `/shop` зі статусом 200 навіть коли вміст показує 503-стан; транспортний статус збережено на BFF. Переводити page-level HTTP-статус через додатковий мережевий запит у middleware зараз не стали.

При 503 входу користувач бачить тимчасову недоступність замість «неправильний пароль». Невдалий logout не скидає локальний auth-стан. Якщо checkout втратив відповідь або отримав 502/503/504, форма й кошик залишаються; інтерфейс просить перевірити історію перед повтором. До C3 немає ідемпотентного checkout, тому автоматичний повтор не робиться.

Тести `tests/c1-2-errors.test.cjs` перевіряють розділення empty/401/404/503/502, заголовки й cookie. Повний протокол `sid/jti`, single-flight refresh, реакція на зміну користувача та rate limit належать C1.3–C1.5. Схема API v1 і її контрольна сума з C1.1 не змінювалися.
